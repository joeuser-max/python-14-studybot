# AI 協作紀錄

## 協作方式

開發期間使用生成式 AI 協助需求分析、架構設計、
程式撰寫、測試設計、除錯與文件整理。
AI 輸出需經人工判斷、修改及實際測試。

以下提示詞為開發過程的摘要，非逐字對話轉錄。

| 階段 | 提問方向 | AI 協助內容 | 人工判斷與修正 |
|---|---|---|---|
| 需求分析 | 如何降低學生規劃與補筆記的成本？ | 功能拆分、規格與資料格式 | 確立主動式 LINE 學習回饋流程 |
| 排程設計 | 如何避免重新排程覆寫人工安排？ | 排程規則與衝突驗證 | 手動安排與自動填滿分離 |
| 介面設計 | 如何讓讀書計畫容易調整？ | 七日拖排元件與視覺化 | 保留日週月檢視及半小時操作 |
| AI 應用 | 如何將筆記疑問轉為可執行任務？ | 結構化摘要及任務候選 | 每題獨立確認，不自動寫入排程 |
| LINE 整合 | 如何讓網頁與 LINE 共用個人資料？ | 登入、Webhook 與資料隔離 | 實機測試登入、筆記與提醒 |
| 自動化 | 如何避免重複提醒及全體重排？ | Worker、去重與局部排程 | 使用者授權、保留其他任務 |
| 系統除錯 | 如何確認整合沒有破壞既有功能？ | 回歸測試及錯誤分析 | 根據實際執行結果修正程式 |

## 產品內建 AI

ClassPulse 可在使用者同意後呼叫 Gemini，
將課後筆記整理為摘要、重點與待釐清問題。
使用者選擇接受的問題才會轉成讀書任務。

規則式排程與 AI 分析是不同模組。
離線展示使用明確標示的模擬結果。

## 學習成果

- 將大型需求拆解為可測試的小型模組。
- 使用 Git 分支及 Pull Request 管理協作。
- 理解 API、Webhook、資料驗證與身份隔離。
- 透過回歸測試確認 AI 產生的程式是否符合需求。
- 理解模型輸出不能取代確定性的工程驗證。

## 限制

不提交 API 金鑰及使用者私人資料。
不將 Mock 結果描述為真實 API 回應，
也不將 AI 產生的建議直接視為正確結果。

## 具體協作案例：從提示詞到驗證

以下問題是既有開發對話的摘要／重述，不是逐字聊天紀錄。以團隊的設計決策、實際修正與驗收為重點。

### 案例一｜學習排程：硬限制與軟偏好

- 提問：如何讓學生手動拖曳單一任務，同時能一鍵填滿剩餘空檔，而不破壞已固定的時段？
- AI 協助：拆分手動放置、偏好標記、整體安排三種操作，提出時間衝突、期限及任務狀態檢查。
- 人工決策：綠色是優先順序，不是唯一允許的時間；未標綠的合法空檔仍可使用。手排僅影響該任務，一鍵安排須明確確認。
- 實作與驗證：`week_planner.py`、`tests/test_schedule_preferences.py` 及瀏覽器互動測試。CI 實際檢查七日板、拖曳與伸縮等操作。
- 學習：先區分不可違反的約束與可調整的偏好，才能解釋演算法的決策，而不是以 AI 推論替代驗證。

### 案例二｜AI 讀書任務：人機共同決策

- 提問：如何從一份筆記的多個疑問產生複習任務，避免 AI 自動新增不必要的工作或擅自修改課表？
- AI 協助：結構化摘要、重點、疑問與任務候選；設計來源筆記關聯、疑問去重及候選確認流程。
- 人工決策：逐題接受／略過；已接受的疑問預設形成 30 分鐘紫色待排卡，期限為下一次該課開始前。模型分析須本次授權，失敗仍保留原始筆記。
- 實作與驗證：`ai_assistant.py`、`note_tasks.py`、`line_bot.py`；以 `tests/test_note_task_lifecycle.py` 等測試檢查候選生命週期。真實 Gemini 曾在封存的內部展示版本操作；離線 CI 不使用真實 API。
- 學習：LLM 適合處理語意與非結構化資料；資料關聯、授權、時間與去重仍須用可測試的確定性規則。

### 案例三｜整合測試：重新安排同一時段識別

- 提問：主線合併後，為何同一 availability ID 的新讀書時段沒有收到新的開始或結束提醒？
- AI 協助：依失敗測試追蹤提醒 ID 與原時段的關聯，指出只看 task ID 和 slot ID 無法區分改期。
- 人工決策與修正：保留既有已發送紀錄及 retry key，將實際開始／結束時間納入新提醒識別，並維持其他固定任務的安排。
- 實際驗證：合併初期 226 passed、2 failed；修正後 228 passed；再納入相容的課後提醒測試，完整整合為 230 passed（macOS）。合併版本見 [PR #22](https://github.com/joeuser-max/python-14-studybot/pull/22)。
- 學習：測試失敗揭示資料識別契約，而不只是語法錯誤；不能為了使測試綠燈而刪除失敗案例。

### 案例四｜Windows 跨平台驗證

- 提問：如何讓 Windows 組員不需要 macOS 的服務腳本或其他人的 API 金鑰，也能執行測試和 Demo？
- AI 協助：建立 Windows/Linux CI matrix、跨平台瀏覽器診斷路徑、PowerShell 啟動方式，分析 CI 真實錯誤。
- 人工決策與修正：首輪 Windows CI 因 Linux 專用 `pwd` 在測試載入階段 import 而失敗；延後至 Linux runtime 才載入，保留 Linux 部署限制；Windows socket 使用獨占綁定。僅略過兩項 POSIX 權限測試，不關閉其餘測試。
- 實際驗證：[CI #279（首輪）](https://github.com/joeuser-max/python-14-studybot/actions/runs/46084248234) → [CI #280（修正後）](https://github.com/joeuser-max/python-14-studybot/actions/runs/46084415055)。Linux 230 passed，Windows 228 passed、2 skipped，兩者 Chromium UI 與 Streamlit HTTP 檢查皆通過。
- 學習：跨平台相容不能僅憑 Python 語法或在單一作業系統上成功判定，需對實際目標環境驗證。

## 開發 AI 與產品 AI 的區別

| 項目 | 開發協作 AI | ClassPulse 內建 AI |
| --- | --- | --- |
| 輸入 | 需求、程式、測試與除錯問題 | 本次同意後的課名、筆記文字及理解自評 |
| 輸出 | 設計建議、程式修改、測試案例與文件 | 摘要、重點、待釐清問題、主題及複習候選 |
| 人工判斷 | 審查修改、實際執行測試、決定是否合併 | 決定是否同意分析及接受每個疑問任務 |
| 確定性程式 | Git、測試、CI | 身份、去重、來源關聯、期限、衝突與提醒 |

相關使用流程見 [圖解使用手冊](user-guide.md)。測試證明的是指定程式行為，不代表正式多使用者部署、外部服務可用性或學習成效已獲驗證。
