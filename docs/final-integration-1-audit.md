### 分清「新需求差異」與「已有 Bug」

- 組員原本的勾選時段若依其原功能設計只是 **Availability**，不能事後說它原本就是 Bug。它只是不符合我們新定義的 **Preference 軟目標**；因此本次沒有把組員勾選 UI 複製進來。
- 以既有逐欄 LINE 輸入重新選課，對「臨時收到任意筆記」的情境造成不必要操作。這屬**使用者流程缺口**，因此建立未分類筆記收件箱，而非刪除原有補筆記精確課次流程。
- 對已手動固定的 V2 任務執行 **Legacy 全表重新安排**，會破壞 V2 的明確手動意圖。因此這是**新整合下必須修正的相容性風險**；現在改為單項重排。已更新歷史回歸測試，並新增手排保護測試。
- 原本網頁 `search_learning_notes` 僅搜尋主題標籤；若直接拿來處理 LINE「搜尋 MOS」，正文有 MOS 仍可能查不到。此為**搜尋介面預期與既有函式契約不合**，因此 LINE 查詢新增正文搜尋而保留既有網頁功能。

## 3. 排程規則（不得退回綠色 Only）

合法候選首先滿足：未過期、七日範圍、Deadline、課表／外部行程／已排任務不衝突、任務不跨非允許時間。綠色集合 `G=Availability∩Preference` 僅為偏好靶，**不屬於 Hard Constraint**。

待排任務先依 Deadline / 同期限剩餘工時排序，每個任務搜尋合法候選；優先評分命中綠色的節數，接著選一天現有讀書負荷較少者，最後才看日期與時段。若全週綠色不存在或已滿，仍用其他合法空檔；而不是拒絕排程。每次畫筆開啟需使用者明確按「一鍵安排」，修改/清除不依週期強制重設。

**已明確界定的 MVP 限制：**這是局部、多目標啟發式搜尋，仍不是已證明全域最優的整數最佳化 Solver，不能宣稱最大化客觀學習效率。

## 4. LINE 與網頁責任

LINE 為輸入、通知、快速查詢及進度回報介面；網頁是唯一課表主控台（日/週/月、七日拖排、ICS、筆記庫、統計、同儕 JSON/AI Coach）。LINE 的 PDF/DOCX/TXT 為**已可擷取文字**的檔案；掃描型 PDF 不進行 OCR。課表仍從網頁匯入 ICS，不從 LINE 圖片自動辨識。LINE AI 的 OpenAI API 可能計費；Gemini Coach 另為可選 API。所有真實 API 都需外部憑證與同意，Mock 測試不等於端到端成功。

目前本機 JSON 與單一使用者，**尚未完成多帳號登入、雲端持久資料庫、正式 HTTPS LINE→Streamlit 身份驗證或真實 LINE Push 實測**。部署是下一階段，不能宣稱已完成。
